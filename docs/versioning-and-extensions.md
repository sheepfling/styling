# Versioning and shared extension policy

The shared renderer currently accepts composition recipe versions `0.1.0`, `0.2.0`, and `0.3.0`. Each version has a closed accent grammar. Typography suite `0.5.0` names the common output slots and 17 semantic roles. A family source package pins its own inputs and chooses which shared version it uses.

Visual representation `0.2.0` adds exact JPEG raster sources for linked native SVG proofs. Earlier `0.1.0` records remain PNG-only and continue to validate unchanged. Native vector builds emit `0.2.0`; the starter and older packages can retain `0.1.0`.

Family-system assembly `0.1.0` joins pinned native and recipe build packets by explicit route and source-package identity. Product-story system `0.1.0` is an optional companion for connected front/back products, replaceable raster stages, identity text, concept facets and cross-product links. Neither changes the recipe grammar or old PDF bytes. Changes to their accepted manifest fields, status meanings, or stage checks require an explicit contract version and fresh audits of affected family packets.

Additive shared accent kinds, changed accepted fields, or new output declarations require an explicit recipe or contract version. Correctness fixes that alter rendered bytes require a new build and visual review for affected family outputs even when the recipe schema does not change. An old recipe must keep its accepted input set and native serializer behavior until a documented migration retires it. Deprecation needs an inventory of active family packages, a replacement path, and a reviewed comparison; simply changing the default is insufficient.

A family may keep native LaTeX composition, typography effects, bespoke marks, and illustration methods in its own source. Promote a shared helper only when it has a bounded, family-neutral job that at least one real family needs. An extension proposal records the intended geometry or validation behavior, physical limits, source and output provenance, compatibility effects, and how its SVG/TikZ or other outputs are reviewed. Use synthetic public examples; keep private copy, assets, and typeface decisions with the family.

Before migrating an expressive family, save the current rendered pages and a short list of signature visual features. Compare the new pages at their intended size. A migration succeeds only when the family still looks like itself and the exact changed bytes receive a fresh review. The common five-slot deliverable contract is a coverage interface, not a mandate to reuse one editorial layout.
